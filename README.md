# ReZonate

A personal, audio-first music recommender. It learns **one** listener's taste from how
songs *sound* (pretrained audio embeddings), not from what's popular, and it reserves part
of every batch for deliberately unfamiliar picks, so niche music has a way in.

Everything runs locally in Python with free/open tools. Candidate audio comes only from
legal sources: your own DRM-free files, the Free Music Archive (FMA), Jamendo (Creative
Commons), and Bandcamp purchases you add by hand.

> **Status:** the full pipeline runs end-to-end on a 1,240-track FMA sample with a
> *simulated* listener (all numbers below come from that). Nothing has seen your data yet.
> The next step is yours: `inspect-export`, then `rate --seed 150`.

## 1. Plan and repo structure

| Phase | What | Where |
|---|---|---|
| 0. Ingest | Apple Music export (plays + Loved/Disliked), local DRM-free audio, FMA sample, Jamendo | `ingest/` |
| 1. Labels | Fuse explicit ratings > Loved/Disliked > implicit plays/skips into grades 0–3 | `labels.py` |
| 2. Embed | CLAP and MERT on identical windows; compare; choose a view | `embed/` |
| 3. Taste | kNN baseline → learned ranker → Bayesian online model | `taste/` |
| 4. Context | Tags, era, lyrics (and popularity, for ablation only) | `features/`, `enrich/` |
| 5. Explore | Batch = exploit (MMR-diversified) + exploration slots | `explore.py` |
| 6. Evaluate | Repeated K-fold NDCG@10 vs popularity & random; bootstrap CIs | `eval/` |
| 7. Feedback | One-key rating CLI with audio; notebook for exploration | `cli.py`, `notebooks/` |

## 2. Quickstart with your data

Needs `ffmpeg` on PATH (decoding and playback) and Python 3.12.

```bash
uv sync --extra embed --extra notebook --extra dev
export LASTFM_API_KEY=...          # free; tags + popularity baseline
export JAMENDO_CLIENT_ID=...       # free; optional extra candidate pool

# 1. Look at your export BEFORE ingesting (Apple doesn't publish the schema)
uv run rezonate inspect-export ~/Downloads/Apple_Media_Services
uv run rezonate ingest-apple   ~/Downloads/Apple_Media_Services

# 2. Audio: your DRM-free files (CD rips, Bandcamp, iTunes Store purchases) + candidates
uv run rezonate ingest-local ~/Music/DRM-free
uv run python scripts/fetch_fma_sample.py --per-genre 100 --per-subgenre 300 --background 3000
uv run rezonate jamendo-probe --tags postpunk      # check field names once
uv run rezonate jamendo-fetch --tags "postpunk indie dub soul" --pages 3

# 3. Enrich, embed (overnight is fine), compare
uv run rezonate enrich --lastfm
uv run rezonate embed --model clap
uv run rezonate embed --model mert                  # optional, ~4x slower on CPU
uv run python scripts/compare_embeddings.py

# 4. Cold start, then normal batches
uv run rezonate rate --seed 150
uv run rezonate rate
uv run rezonate evaluate --views clap
```

**The DRM issue.** Apple Music subscription downloads are FairPlay-protected and can't be
decoded, so your Loved songs carry no audio by default. They still help in three ways:

1. any DRM-free copy you own (`ingest-local`) is linked by artist+title and inherits the label;
2. the **CLAP text bridge** (experimental): a loved song's Last.fm/MusicBrainz tags become
   text ("indie pop, dark pop, electropop music"), which CLAP's text tower embeds into the
   *audio* space as soft-weighted anchors. In `reports/text_bridge_check.md`, anchors built
   from genre-style text rank the catalogue almost as well as the songs' real audio
   (NDCG@50 0.40 vs 0.42; random 0.27). Built from FMA's noisy free tags they're at chance
   (0.27), so only Last.fm/MusicBrainz tags are used. The good case is optimistic (see that
   report), so treat the bridge as a prior that your ratings override;
3. they provide the artist/era/tag context and the popularity baseline.

I deliberately did **not** use 30 s store previews (iTunes Search API, Spotify). Apple's
(archived) terms limit previews to promoting store content, and Spotify removed preview URLs
and audio features for new apps in Nov 2024.

## 3. Audio embeddings: CLAP vs MERT

Compared on 440 FMA clips (11 genres × 40), with identical 10 s windows for both models
(`scripts/compare_embeddings.py` → `reports/embedding_comparison.md`).
[MERT-v1-95M](https://huggingface.co/m-a-p/MERT-v1-95M) was scored per layer. CLAP is
[`laion/larger_clap_music_and_speech`](https://huggingface.co/laion/larger_clap_music_and_speech).

| view | genre probe F1 | kNN P@10 | sub-genre Jaccard@10 | raw anisotropy |
|---|---|---|---|---|
| chance | 0.09 | 0.09 | 0.05 | — |
| **CLAP** | **0.54** | **0.45** | **0.31** | 0.20 |
| MERT best layer (L6) | 0.51 | 0.31 | 0.21 | 0.78 |
| MERT mean of 13 layers | 0.46 | 0.28 | 0.19 | 0.81 |

On a held-out half (MERT layer picked on the other half): CLAP 0.39 kNN P@10, MERT-L8 0.26,
concat 0.37.

**Choice: CLAP as the default view.** The gap is small for a *linear probe* (style is
linearly decodable from both), but large for *nearest neighbours*. The kNN baseline and the
RBF basis of the Bayesian model depend on local neighbourhoods, so that's the metric that
matters here. MERT's raw space is very anisotropic (mean cosine 0.78 between random clips),
which compresses similarities. Centering helps but doesn't close the gap. Mid layers (6–8)
are best, as the MERT paper suggests for genre-like tasks. Concatenation adds nothing on this
sample. CLAP is also ~4.8× cheaper on CPU (0.44 vs 2.12 s per track, 3 × 10 s windows, 4 threads), and its text tower enables
the cold-start bridge.

Caveats:
- Genre is a proxy, not your taste. The taste evaluation (§7) runs with all three views.
- CLAP was trained with text supervision that likely includes genre words, which favours it
  on genre-based metrics.
- I tested the 95M MERT with mean pooling. MERT-330M or learned attention pooling might
  narrow the gap. `rezonate embed --model mert` plus the `mert:L<i>` views make that easy
  to try on your own ratings.

## 4. Taste models and trade-offs

| | kNN baseline | Learned ranker | Bayesian online model |
|---|---|---|---|
| Idea | mean top-k similarity to liked − β·to disliked | regularised logistic over PCA(audio) + leave-one-out kNN scores + context | Bayesian logistic regression on `[PCA, RBF bumps on catalogue landmarks, context]`, Laplace posterior |
| Multi-modal taste | ✅ native (local, not a centroid) | via kNN features | ✅ RBF basis = several taste regions |
| Uses context | ✗ | ✅ | ✅ |
| Updates per rating | instant (store the label) | refit (seconds) | ✅ warm-started Newton step (ms) |
| Uncertainty | ✗ | ✗ (calibrated-ish probs) | ✅ posterior variance → Thompson / UCB |
| Data hunger | lowest | highest | medium (prior regularises) |
| Failure mode | hubs; can't weigh features | overfits <~200 labels | basis choice; linear in basis |

* **Why not a single "taste vector"?** You said your taste has several clusters. The
  average of post-punk, R&B and dub vectors lands somewhere you don't like. kNN and the RBF
  basis both score *locally*. `KNNTaste.modes()` exposes the clusters (silhouette-picked
  k-means) for explanations, diversity and exploration.
* **Why pointwise, not LambdaMART?** Learning-to-rank losses compare items within a query,
  and you are the only query. With a few hundred labels a pairwise loss adds variance, not
  information. `LearnedRanker(kind="gbt")` is there for when you pass ~1k labels.
* **Why Bayesian at all, if kNN is close on NDCG?** Because it's the piece that knows what
  it *doesn't* know. Exploration slots use posterior draws (Thompson sampling), so "unfamiliar"
  picks are uncertain, not just random. It also updates after every keypress in the rating loop.
* **Labels.** Grades: 0 dislike, 1 meh, 2 like, 3 love. Priority: CLI rating > Apple
  Loved/Disliked > implicit. Implicit rules are conservative (`labels.py`). A skip needs an
  early exit (<50 % or <30 s) with a skip/manual end reason. A "like" needs ≥3 complete
  plays on ≥2 distinct days, because one binge isn't taste. Little evidence means no label.

## 5. Context features (tags, era, lyrics)

Four feature groups (`features/context.py`), each switchable for ablation:

* **tags**: TF-IDF over Last.fm top tags, MusicBrainz tags, and FMA/Jamendo tags, reduced
  to 16 dims with SVD, plus a has-tags flag. Missingness is a feature because niche tracks
  have fewer tags.
* **era**: release decade one-hot, z-scored year, missing flag. MusicBrainz era is the
  *earliest* date across matching recordings.
* **lyrics**: LRCLIB plain lyrics → `all-MiniLM-L6-v2` → PCA 16, plus instrumental and
  missing flags. You said lyrics are secondary, so their weight is learned, not fixed.
* **pop**: log popularity z-scored within source. **Off by default.** Included only to show
  what it does.

Ablation on the simulated listener, with paired differences on the same 30 folds
(`reports/eval_simulated.md`):

| added to CLAP audio | Δ NDCG@10 (95 % CI) | folds won | effect on niche-ness |
|---|---|---|---|
| tags (ranker) | **+0.081** [+0.044, +0.118] | 25/30 | top-10 popularity pct 0.51 → 0.56 |
| tags (Bayes) | **+0.064** [+0.025, +0.099] | 22/30 | 0.50 → 0.56 |
| era | +0.002 [−0.014, +0.018] | 12/30 | none |
| lyrics | −0.000 [−0.010, +0.009] | 11/30 | none (1.7 % coverage) |
| era + lyrics on top of tags | −0.008 [−0.025, +0.008] | 15/30 | — |
| popularity (Bayes) | **+0.057** [+0.026, +0.089] | 23/30 | **0.50 → 0.67** |

How to read this:
- **Tags help clearly.** They're also the most leakage-prone group, because FMA tags often
  name the genre and the simulated listener is defined by genre. Expect a smaller gain on
  your data.
- **Era does nothing here, and that's the right answer.** The simulated listener has no era
  preference, and the model didn't invent one. On your data (older Linkin Park, 1970 Free)
  it may matter. I can't tell from this test.
- **Lyrics: inconclusive, not negative.** LRCLIB matched 21 of 1,240 FMA tracks (19 with lyrics, 2 instrumental). Your
  library should have far higher coverage, so re-run the ablation with
  `rezonate evaluate --context-groups tags,era,lyrics`.
- **Popularity raises NDCG and drags picks toward the mainstream.** The simulated listener
  has a mild popularity pull, so ranking popular songs higher pays off in NDCG. It also
  moves the top 10 from the 50th to the 67th popularity percentile. That's the
  mainstream-recommender failure mode you want to avoid, so it stays off by default.

## 6. Exploration

Each batch (default 20) reserves `explore_fraction` (default **25 %**) of its slots for
exploration. Picks are chosen in three filters (`explore.py`):

1. **Unfamiliar**: max cosine similarity to anything you've rated or played must be in the
   bottom 30 % of the pool. That rules out "more of the same".
2. **Under-covered region**: the catalogue is k-means clustered, and clusters are visited
   in order of *fewest ratings per track*, so a region you've never heard gets one probe
   before a known region gets a fifth.
3. **Not hopeless**: inside the cluster, take the best **Thompson sample** from the
   Bayesian posterior. Tracks the model is unsure about can win. Tracks it's confident you'd
   dislike rarely do.

Exploit slots use MMR (λ = 0.75) so one taste mode can't fill the batch. The batch is
shuffled so you can't tell which slots are exploratory, which avoids rating bias, and every
rating is logged with `context = explore | exploit`. The CLI prints the explore hit rate,
so `explore_fraction` can be tuned from your data. Optional `--niche-bias` breaks near-ties
toward less popular tracks.

**Does it pay off?** This is an online simulation on the simulated listener
(`scripts/simulate_online.py`, `reports/exploration_simulated.md`). The listener starts
with 30 ratings from only 2 of their 7 taste modes, then gets 10 batches of 20, over 8 seeds:

| scenario | ε | hit rate | rounds to find a new mode ↓ | final catalogue NDCG@50 |
|---|---|---|---|---|
| full pool (liked music common) | 0 | 0.52 | 3.5 | 0.43 |
| | **0.25** | 0.49 | **2.0** | 0.46 |
| niche (each new mode = 12 tracks) | 0 | 0.67 | 6.7 | 0.39 |
| | **0.25** | 0.59 | **5.4** | **0.52** |
| | 0.5 | 0.48 | 4.9 | 0.53 |

In the niche case, ε = 0.25 beats ε = 0 on final model quality in **8/8 seeds** and finds
new modes faster in 7/8. The price is about 8 points of hit rate. That's the expected
explore/exploit trade: some batch slots go to probes, and the model learns more about you
from them. ε = 0.5 buys little extra model quality for a much bigger hit-rate cost, so
0.25 is the default. Tune it once your explore hit rate is logged.

## 7. Evaluation

Protocol (`eval/protocol.py`): repeated stratified K-fold over **rated** tracks. Train on
4/5 of the labels, rank the held-out 1/5, and compute NDCG@10 with gain 2^grade − 1.
Unrated tracks are never treated as negatives. CIs are percentile bootstraps over folds.
Baselines are **popularity** (FMA/Jamendo listens or Last.fm listeners, as a within-source
percentile) and **random**. `top10_pop_pct` is the mean popularity percentile of a model's
top 10, a direct read on "does it surface niche songs?".

Simulated listener: 1,240 FMA tracks; 300 random tracks rated per persona; 3 personas ×
5 folds × 2 repeats = 30 folds.

| model (audio only) | NDCG@10 | 95 % CI | P@10 like+ | top-10 pop pct |
|---|---|---|---|---|
| kNN, CLAP | **0.488** | [0.447, 0.532] | 0.62 | 0.48 |
| Bayes, CLAP | 0.481 | [0.443, 0.518] | 0.57 | 0.50 |
| Ranker, CLAP | 0.473 | [0.427, 0.518] | 0.59 | 0.51 |
| kNN, CLAP+MERT-L8 | 0.491 | [0.455, 0.528] | 0.60 | 0.47 |
| Bayes, MERT-L8 | 0.438 | [0.407, 0.468] | 0.52 | 0.47 |
| **popularity** | 0.417 | [0.359, 0.470] | 0.45 | **0.92** |
| random | 0.265 | [0.226, 0.304] | 0.34 | 0.50 |
| *best with context:* Ranker, CLAP + tags | 0.554 | [0.513, 0.591] | 0.63 | 0.56 |

Paired comparisons on the same folds:
- **Taste models vs popularity: +0.06 to +0.07 NDCG@10, but the 95 % CI includes 0**
  (kNN +0.072 [−0.006, +0.154], 18/30 folds). Popularity is a strong baseline on this
  simulated listener because they have a built-in popularity pull. The audio models match
  or beat it *while recommending from the middle of the popularity distribution* (50th
  percentile vs 92nd), which is the point of the project. With tags the gap widens
  (0.554 vs 0.417).
- **CLAP vs MERT** (kNN): +0.082 [+0.045, +0.123], 23/30. Consistent with §3.
- **kNN vs ranker vs Bayes** (audio only): no detectable difference (|Δ| ≤ 0.015, CIs span
  0). At ~240 training labels the simple baseline is as good as the learned models. The
  Bayesian model earns its place through uncertainty (§6) and online updates, not offline
  NDCG.

What to expect on your data: 150 seed ratings plus loves gives roughly 30–60 held-out
tracks per fold, so CIs will be about as wide as these. Give it a few hundred ratings
before reading much into model-vs-model differences.

## 8. Rating tool

```
$ rezonate rate
0 dislike  1 meh  2 like  3 love   s skip  r replay  q quit
───────────────────────── 1/20 ─────────────────────────
Glass Candy — Brittle Woman   (fma, Attribution-NonCommercial-ShareAlike 3.0 International)
grade 3  P(like) 0.76 -> 0.77  (exploit: score 0.76)
```

* Plays a 30 s excerpt from ~35 % into the track via `ffplay` (`--no-audio` to disable).
* One keypress per song; the Bayesian model updates immediately.
* `--seed 150` gives a cold-start batch: one track nearest each of 150 k-means centroids.
  Coverage matters more than depth when every region is equally unknown.
* The *why* (exploit/explore and reason) is shown only **after** you rate.
* The notebook (`notebooks/01_explore.ipynb`) has embedding maps, your taste modes, a batch
  with inline players, and `rate(i, grade)`.

## 9. Flags: things I'm unsure about

**Verified against current docs or live calls (Nov 2026)**
- LRCLIB: `/api/get` params, ±2 s duration matching, User-Agent identification, Retry-After;
  live calls work.
- MusicBrainz: ≤1 req/s and identifying User-Agent; live calls work. The top search hit is
  often a live/remaster version, so era = earliest date across matching recordings
  ("In the End" → 2001, not 2007).
- Last.fm `track.getTopTags` parameters (official page).
- Spotify: audio features, recommendations and previews were cut off for new apps
  (Nov 27, 2024).
- FMA: archive URLs, `tracks.csv` layout; Range reads work.
- Model cards: MERT-v1-95M is **CC-BY-NC-4.0** (fine personally, not commercially), 24 kHz,
  13 layers. CLAP is Apache-2.0, 48 kHz.

**Not verified, so check before relying on them**
- **Apple Music export schema.** Column names and End Reason values come from community
  sources, not Apple. Run `inspect-export` first and pass `--overrides` if a column
  doesn't resolve. In particular, I'm assuming that `TRACK_SKIPPED_FORWARDS` /
  `MANUALLY_SELECTED_PLAYBACK_OF_A_DIFF_ITEM` mean what they say.
- **Jamendo** field names beyond `client_id` and `audiodownload_allowed` (the docs site was
  unreachable from my sandbox), plus the ~35k requests/month quota. `jamendo-probe` prints a
  raw response to check them.
- Last.fm `track.getInfo` → `listeners` (from client libraries, not official docs).
- The CLAP **text bridge** for DRM-only loves: checked only on the simulated listener,
  with an optimistic genre-word proxy for Last.fm tags (`reports/text_bridge_check.md`).

**Found along the way**
- `laion/larger_clap_music` on Hugging Face is **broken**. It loads cleanly but has
  logit scale ≈ 1.0, text embeddings that are all ~0.999 similar, and chance-level
  zero-shot accuracy. See `reports/clap_checkpoint_check.md`. We use
  `laion/larger_clap_music_and_speech`.
- LRCLIB knows almost no FMA artists (~2 % hit rate), so the lyrics ablation here is
  inconclusive. Expect far higher coverage on your mainstream-leaning library.

**Methodological caveats**
- The simulated listener is defined through FMA genre labels, which both the audio
  embeddings and FMA tags correlate with, so absolute numbers are optimistic. Model *ranking*
  is more trustworthy than levels, and only your ratings answer the real question.
- Selection bias: ratings aren't a random sample (loves are songs you already found; CLI
  ratings are songs the system chose). Explore-tagged ratings are the least biased slice.
- The persona's dislikes (old-time, country, easy listening, spoken word) are placeholders,
  since you left dislikes blank.
